### 1.1 The `core` stage (G-core only)
This narrow stage proves the state machine before any hook code exists:
- **Moves:** class DATA_ONLY with census `data_refs == {}` and `core_refs == {}`. That is 197 at d601443; Heat Wave, Rock Slide and others reference status or volatile handlers and are excluded.
- **Items:** none (empty slot).
- **Abilities:** the 6 DATA_ONLY abilities: Battle Armor, Shell Armor, Corrosion, Early Bird, Levitate and Stall. M2 implements:
  - Levitate in the grounded check;
  - Stall in fractional priority;
  - the Battle Armor / Shell Armor crit veto.
  
  Corrosion and Early Bird are inert without status.
- **Species:** those that can legally hold one of these abilities (20 at d601443, about 15 distinct under Species Clause). No Mega Stones.
- **Extending:** abilities can be added to `tools/datagen/core_inert.json` only through an ADR showing CBR = 100% on 10k core battles with that ability present and ignored by the engine.
- **Expectation:** the pool is narrow. G-core proves the state machine, not coverage.

## 2. The mechanics catalogue (`docs/catalogue.csv`)

- **Seed.** `design/catalogue.csv` is generated by `design/tools/make_catalogue.py` from the research outputs. It has 1,025 rows: 510 moves, 215 abilities, 166 items, 102 conditions and 32 ENGINE_DELTA/SYSTEM rows.
- **Ownership.** Copy it into the repo, then regenerate the entity columns with the repo's datagen on each re-pin. Status columns are preserved by merging on (kind, id).

**Columns:**
- `kind`, `id`, `name`;
- `class` (DATA_ONLY / DATA_PLUS_COMMON / CUSTOM / SYSTEM);
- `stage` (v0 / v1 / v2 / `dep` for conditions: implemented when the first dependent lands);
- `hooks` (PS handler keys; `cond.*` = the entity's own condition);
- `n_fns`, `loc`, `core_refs`, `complexity`;
- usage columns, `notes` (notorious interactions);
- `status`, `ps_commit`, `scenario_tests`, `fuzz_hits`.

**Status values:**

| Status | Meaning |
|---|---|
| `todo` | not started |
| `wip` | in progress |
| `impl` | code done, scenario test passing |
| `done` | ADR-026 satisfied: ≥ 50 fuzz hits and 0 open divergences |
| `blocked:<reason>` | blocked |
| `deviates:<ADR>` | intentional deviation from PS |

`harness/report.py` fills `fuzz_hits` from coverage counters, and fails CI if a `done` row's hits drop below threshold or a divergence bucket references it.

## 3. Handler classification pipeline

1. **Census.** `tools/datagen/census.js`, ported from `research/dex/scripts/handler_census.js`, lists every function-valued key per entity together with its normalised template hash.
2. **Classify each handler** into:
   - `ROW_MUL`: a multiplier contributor with a predicate from the library (04 §6.3);
   - `ROW_GATE`: a predicate gate with a result code;
   - `ROW_REPL`: a constant replacement;
   - `ROW_DURATION`: duration-only, or a durationCallback kind;
   - `BESPOKE`: needs a switch branch.
   
   The first pass is automatic, using MV §7.3 heuristics plus template sharing. Then a human or agent review pins each one in `tools/datagen/handler_classification.json` as `{entity, hook, prefix, class, predicate, params, notes}`.
3. **Codegen.**
   - Rows are emitted into `vgcjax/data/hook_rows.npz` (the only rows file).
   - For each BESPOKE handler, codegen writes a **reference stub** into `vgcjax/data/handlers_stub.py`. Generated files are never edited.
   - `tools/datagen/scaffold.py <entity>` copies the stub into the right `vgcjax/effects/*.py` module, where the implementer fills it in:
     ```python
     @handler(hook=H.TRY_HIT, effect=E.MOVE_PROTECT, ps="data/moves.ts:14010-14060")
     def protect_try_hit(ctx, state, dex):   # -> (relay, ctx, state)
         ...
     ```
   - The registry builds `hook_local_idx` and the per-hook branch tuples.
   - A static test checks that every BESPOKE row of the current stage has exactly one registered implementation.
4. **Template sharing.**
   - Handlers with the same template hash share one Python function, parameterised by per-entity constants from a table. Examples: 18 resist berries, the -ate abilities, pinch abilities, Static / Flame Body / Poison Point.
   - This keeps v1 at about 600 branches rather than about 900 functions.

## 4. Implementation order (within each stage, by dependency then usage)

**v0 order.** Each step's scenario tests and conformance subset must pass before moving on:
1. **Core:** damage, typing, stats, boosts, accuracy and evasion, crits, PP, Struggle, recoil, drain, heal, multihit, OHKO.
2. **Statuses** (Champions values) and core volatiles: confusion, flinch, partial trap, lockedmove, mustrecharge, twoturnmove, choicelock.
3. **Protect family:** stall, Wide Guard, Quick Guard, Feint. Then Fake Out, including the [C] mask.
4. **Field:** weather (sun, rain, sand, snow) with setters, rocks and weather abilities. Terrain (Electric, Grassy, Psychic) with Surges, seeds, Grassy Glide, Expanding Force and the Psychic Terrain priority block.
5. **Speed control:** Tailwind, Trick Room [C], Icy Wind and Electroweb, paralysis, the Choice Scarf ModifySpe chain, Quick Claw / Quick Draw.
6. **Switching:** U-turn, Volt Switch, Flip Turn, Parting Shot, Baton Pass, Shed Tail; Eject Button [C]; Emergency Exit [C]; Red Card and drag moves; hazards; Regenerator, Natural Cure.
7. **Intimidate and the boost-reaction web:** Defiant, Competitive, Clear Body family, Mirror Armor, White Herb, Rattled.
8. **Redirection:** Follow Me, Rage Powder, Lightning Rod. Helping Hand, Ally Switch.
9. **Mega Evolution** end to end, including Mega abilities that fire on Mega and the new [C] abilities present in v0.
10. **Items:** berries (Sitrus, Lum, pinch berries, resist berries), Life Orb, Focus Sash, Leftovers, Choice Scarf, Rocky Helmet, type boosters, Expert Belt, Light Clay, Mental Herb, …
11. The remaining v0 CUSTOM entities, in descending `p_team_bo3_1760`.

**v1 / v2.** Order by family to maximise template reuse, then by usage. Do the notorious entities (`notes` column) early within their stage, because they stress the framework: Illusion, Transform / Imposter, Encore, Instruct, Revival Blessing, Magic Bounce, Substitute, Disguise / Stance Change / Zero to Hero, Trace / Skill Swap.

## 5. Recipe: implementing one entity (the inner loop)
1. **Read the PS source.**
   - Find the entity in `oracle/ps/data/*.ts` and `oracle/ps/data/mods/champions/*.ts`. The mod overrides base.
   - Grep `oracle/ps/sim/` for its id. `core_refs` in the catalogue lists the sim files that special-case it.
2. **Data.**
   - Confirm datagen exported all its data fields; extend `export_dex.js` if not.
   - Confirm its handlers are classified (§3).
3. **Code.**
   - Implement the BESPOKE handlers with a `ps=` citation.
   - Reuse templates.
   - Never special-case an entity id outside its handler unless PS's `sim/` does the same; then cite that line.
4. **Scenario test** (`tests/scenarios/<family>/test_<id>.py`).
   - Use `oracle.craft` to build a minimal PS state exercising each handler path, with forced outcomes for the relevant draws.
   - Assert engine == PS projection after the turn.
   - Cover every branch the PS code has: each `if`.
5. **Conformance.**
   - Run a targeted fuzz batch with teams forced to contain the entity: `oracle gen --require <id>`.
   - Iterate until clean.
6. **Catalogue.** Set `status=impl`, fill `scenario_tests` and commit. `done` is set automatically once fuzz hits reach the threshold with no divergences.

## 7. Team restriction
- Training, test and conformance team banks are filtered to the **current stage**: every species, move, ability and item must have `supported = 1`.
- A team-bank build fails if a team violates `TeamValidator` (run through the oracle RPC `validate_team`) or the stage filter.
- At runtime, `ERR_UNSUPPORTED_EFFECT` fires if anything slips through. Count it in EpisodeStats.
